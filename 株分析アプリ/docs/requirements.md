## 2. 背景と目的

### 2.1 背景

株式投資では、価格、出来高、財務情報など複数の情報を継続的に収集し、一貫した基準で判断する必要がある。人手による判断では、確認漏れ、感情による判断、過去の検証不足が起きやすい。

### 2.2 目的

本システムは、日本株の市場データを分析し、定量的な売買候補とその根拠を提示する。また、過去データによるバックテストと仮想売買を通じて、実資金を投入する前に戦略の有効性とリスクを検証できるようにする。

### 2.3 MVPの成功条件

- 対象銘柄の日足データを自動取得・保存できる。
- 同じ入力データと設定から、常に同じ分析結果を再現できる。
- 銘柄ごとに売買スコア、判定、根拠を確認できる。
- 手数料とスリッページを考慮したバックテストを実行できる。
- 仮想ポートフォリオでシグナルに基づく注文・約定・損益を記録できる。
- リスク上限に違反する注文をシステムが拒否できる。
- すべての判断、注文、エラーを監査ログで追跡できる。

## 3. 基本方針

1. 分析、リスク判定、注文執行を独立したモジュールに分離する。
2. MVPでは実口座への自動発注を行わない。
3. 売買判定は説明可能なルールベースから開始する。
4. AIの出力だけを根拠に売買判定または注文を行わない。
5. ポイント・イン・タイムで利用可能だった情報だけを使い、未来情報の混入を防ぐ。
6. データ異常やシステム異常を検出した場合は、安全側に停止する。

## 5. 想定利用者と利用シナリオ

### 5.1 利用者

- 個人利用者1名
- 日本株の分析と仮想運用を行う管理者

### 5.2 主要シナリオ

1. 利用者は市場終了後にデータ更新結果を確認する。
2. システムは対象銘柄を分析し、買い候補、保有継続候補、売り候補を生成する。
3. 利用者はスコア内訳、チャート、判定理由を確認する。
4. 利用者は戦略条件を指定してバックテストを実行する。
5. システムは仮想売買を行い、ポートフォリオと損益を更新する。
6. リスク制限またはデータ異常がある場合、システムは注文を拒否して理由を通知する。

## 6. 業務ルール

### 6.1 売買タイミング

- シグナルは原則として取引日の日足確定後に生成する。
- 当日終値で生成したシグナルは、未来情報の混入を避けるため、翌取引日の始値で約定したものとして扱う。
- 翌営業日判定には取引所カレンダーを使用する。
- 売買停止、上場廃止、値幅制限等により約定できない場合は、未約定または失効として記録する。

### 6.2 初期売買戦略

初期戦略は設定変更可能なルールとして実装する。

#### 買い候補条件

- 終値が200日単純移動平均線より上である。
- 20日単純移動平均線が60日単純移動平均線より上である。
- 当日出来高が20日平均出来高の1.5倍以上である。
- 14日RSIが35以上70以下である。
- 必要な指標を算出できるだけのデータが存在する。

#### 売り候補条件

次のいずれかを満たした場合に売り候補とする。

- 終値が20日単純移動平均線を下回った。
- 終値が平均取得価格から7%以上下落した。
- 取得後最高値から5%以上下落した。ただし、含み益が一度でも15%以上になったポジションに限る。

#### 判定区分

- `BUY_CANDIDATE`: 買い条件と最低スコアを満たす。
- `HOLD`: 保有中で売り条件を満たさない。
- `SELL_CANDIDATE`: 保有中で売り条件を満たす。
- `NO_ACTION`: 上記に該当しない。
- `NOT_EVALUABLE`: データ不足またはデータ異常により判定できない。

### 6.3 スコア

- スコアは0～100点とし、項目別の加点・減点と合計を保存する。
- 初期の買い判定閾値は70点とする。
- スコア計算式と各パラメータにはバージョンを付与する。
- 画面には合計点だけでなく、項目別点数と使用データ日を表示する。
- スコアと売買判定を分け、強制決済ルールはスコアより優先する。

### 6.4 注文数量とリスク制限

初期値は以下とし、設定可能とする。

| 項目 | 初期値 |
|---|---:|
| 1取引の許容損失 | 評価額の0.5% |
| 1銘柄の最大投資比率 | 評価額の10% |
| 同一業種の最大投資比率 | 評価額の25% |
| 最大保有銘柄数 | 10銘柄 |
| 1日の最大損失 | 前日評価額の2% |
| 現金最低比率 | 評価額の10% |
| 初期損切り幅 | 取得価格の7% |
| 売買単位 | 銘柄マスタの単元株数 |

注文数量は次の小さい方を採用し、売買単位未満を切り捨てる。

```text
リスク基準株数 = 1取引の許容損失額 ÷（想定約定価格 - 損切り価格）
集中上限株数   = 1銘柄の最大投資額 ÷ 想定約定価格
注文株数       = min(リスク基準株数, 集中上限株数, 購買可能株数)
```

- 算出結果が1売買単位未満の場合は注文しない。
- 現金、保有数、銘柄集中、業種集中、日次損失の全制限を注文前に再検証する。
- 日次最大損失に達した場合、その日の新規買いを停止する。
- 売却注文は、保有数量を超えてはならない。

### 9.2 保存と品質

- 日付と時刻はDB内でタイムゾーンを明示し、画面では原則として日本時間で表示する。
- 金額・価格は浮動小数点誤差を避ける型で保存する。
- 元データと調整済みデータの関係を追跡可能にする。
- 同一銘柄・取引日の価格は一意とする。
- データ訂正が発生した場合は、更新日時と取得元を記録する。
- バックテスト結果には再現に必要な戦略版、設定、対象データ範囲を保存する。

## 10. 外部インターフェース要件

### 10.1 市場データ連携

- データ提供元は、対象市場、利用目的、自動取得、再配布、保存期間の利用条件を満たすこと。
- APIキー等はソースコードやDBへ平文保存せず、環境変数またはシークレット管理機能で管理する。
- レート制限、タイムアウト、指数バックオフ付き再試行を実装する。
- 提供元障害時は古いデータで新規売買判断を行わない。

## 11. バッチ・スケジュール要件

標準の日次処理順序は以下とする。実行時刻は設定可能とし、取引所カレンダー上の営業日のみ実行する。

1. 銘柄マスタ更新
2. 日足価格更新
3. データ品質検査
4. テクニカル指標計算
5. 売買シグナル生成
6. リスク判定と仮想注文案生成
7. 翌取引日の価格取得後、対象注文の仮想約定処理
8. ポートフォリオ評価
9. 日次サマリー通知

- 前段処理が失敗した場合、依存する後段処理を実行しない。
- 同じ対象日のジョブを再実行しても、価格、シグナル、注文が重複しない。
- ジョブごとに開始、終了、成功、失敗、処理件数を記録する。

## 12. 非機能要件

### 12.1 性能

- 監視対象500銘柄の日次分析を、通常環境で10分以内に完了する。
- 通常の一覧・詳細APIは、キャッシュ利用時の95パーセンタイルで2秒以内に応答する。
- 長時間のバックテストは非同期実行し、進捗を表示する。

### 12.2 可用性・信頼性

- 同一処理の再実行で重複データ・重複注文を作らない。
- 外部APIの一時障害に対して自動再試行する。
- データが最新取引日まで更新されていない場合、新規買いを停止する。
- 例外時は注文を作成せず、処理を失敗として記録する。
- DBは日次バックアップし、復元手順を文書化する。

### 12.3 セキュリティ

- MVPはローカル利用または認証済みの単一利用者に限定する。
- 外部公開する場合は認証、TLS、CSRF対策、レート制限を必須とする。
- APIキー、パスワード等をログに出力しない。
- 設定変更、緊急停止、注文承認を監査対象にする。
- 依存パッケージを固定し、脆弱性検査を定期実行する。

### 12.4 保守性・テスト容易性

- データ取得、指標計算、戦略、リスク管理、約定、UIを分離する。
- 戦略とリスク設定をコード変更なしで調整可能にする。
- 金額、株数、日付境界、休場日について自動テストを用意する。
- 主要処理には構造化ログと相関IDを付与する。

### 12.5 アクセシビリティ・操作性

- 色だけで買い・売り・警告を区別しない。
- 金額、割合、日時、データ基準日を明示する。
- 破壊的または重要な操作には確認を設ける。
- 判定結果には必ず根拠とデータ鮮度を表示する。

## 14. テスト・受入基準

### 14.1 単体・結合テスト

- 各テクニカル指標を既知の入力・期待値で検証する。
- 分割調整前後でリターン計算が不連続にならないことを検証する。
- 土日、祝日、臨時休場、うるう日を含む日付処理を検証する。
- 同じ日次処理を2回実行してもデータ・注文が重複しないことを検証する。
- 現金不足、単元未満、集中上限、日次損失上限の注文が拒否されることを検証する。
- 当日終値のシグナルが当日終値で約定しないことを検証する。
- 緊急停止中に新規注文が作成・執行されないことを検証する。

### 14.2 MVP受入条件

1. 指定した500銘柄について、直近3年以上の日足を登録できる。
2. 市場終了後の日次ジョブが、データ取得からシグナル生成まで自動完了する。
3. 任意銘柄のチャート、指標、スコア、判定理由を画面で確認できる。
4. 期間、初期資金、手数料、スリッページを指定したバックテストを実行できる。
5. バックテスト結果から、全約定と日次評価額を追跡できる。
6. 仮想注文案を承認し、翌取引日の価格で約定・ポートフォリオ更新できる。
7. リスク上限違反の注文は拒否され、画面とログに理由が残る。
8. データ欠損・更新失敗時は新規買いを停止し、通知される。
9. 戦略設定変更前後の内容と、各シグナルが使用した設定版を追跡できる。
10. 自動テストが成功し、重大度の高い既知不具合がない。

## 15. 開発フェーズ

### Phase 1: 分析基盤

- プロジェクト基盤、DB、銘柄・価格データ
- 指標計算、スコア、銘柄一覧・詳細
- データ品質検査、日次ジョブ

### Phase 2: バックテスト

- 注文・約定シミュレーター
- 手数料・スリッページ・ポジション管理
- 成績指標と結果画面

### Phase 3: 仮想運用

- 仮想口座、注文承認、日次約定
- リスクエンジン、通知、緊急停止
- 監査ログ、運用監視

### Phase 4: 実取引の検討

- 最低3か月の仮想運用結果をレビューする。
- バックテストと仮想運用の乖離原因を分析する。
- 証券会社API、利用規約、データライセンス、法令・税務を確認する。
- 実取引用の追加要件定義とセキュリティレビューを行う。

## 16. リスクと対策

| リスク | 主な対策 |
|---|---|
| 過剰最適化 | 未使用テスト期間、少ないパラメータ、複数相場局面で検証 |
| 未来情報の混入 | 翌日約定、発表日時ベースのデータ、ポイント・イン・タイム検証 |
| 生存者バイアス | 可能な限り上場廃止銘柄と当時の構成銘柄を含める |
| データ欠損・誤り | 品質検査、取得元記録、異常時停止 |
| 約定モデルが楽観的 | 手数料・スリッページ、売買停止・未約定のモデル化 |
| 損失集中 | 取引、銘柄、業種、日次損失の上限 |
| 重複注文 | 冪等キー、注文状態管理、DB一意制約 |
| 外部API障害 | 再試行、タイムアウト、サーキットブレーカー、通知 |
| 秘密情報漏えい | シークレット管理、マスキング、最小権限 |
| ルール・規約違反 | 使用前に証券会社・データ提供元の最新規約と関係法令を確認 |
